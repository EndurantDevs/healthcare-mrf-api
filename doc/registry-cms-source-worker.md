# CMS source notification worker

`python -m process registry-cms-source-worker` consumes one exact, immutable source notification and exits. The operator supplies a closed JSON document through `HLTHPRT_REGISTRY_CMS_SOURCE_WORKER`; command arguments are unsupported. Do not put credentials on the command line or in logs.

The document requires `execution_dsn`, `notification_dsn`, `source_schema`, `receipt_id`, `notification_sha256`, `consumer`, and `notification_store`. Optional `source_endpoint_id` is a nonempty printable Source endpoint identity bounded to 64 UTF-8 bytes; control dispatch requires it. Explicit CLI mode remains compatible without it. It accepts at most 16 KiB of UTF-8 JSON. Duplicate and unknown fields, invalid types, unsupported connection options, and ambiguous roles refuse before resources open. Both DSNs must identify the same endpoint, database and TLS mode. The worker also verifies the actual database, server start identity and both schema OIDs on native connections.

`consumer` requires `control_schema`, `execution_role`, `owner_role`, `coordinates`, and `replaced_coordinates`. Both coordinate objects contain exactly `source_system`, `source_id`, `dataset_schema`, `dataset_id`, `producer_id`, and `edition_id`. They identify the complete new source and exact old replacement slot. Optional `loader_roles` and `reader_roles` are arrays of distinct configured role names. `max_attempts` defaults to 2 and accepts integers 1 through 3; `operation_seconds` defaults to 300 and accepts integers 1 through 3600. These are the connected consumer's bounded attempt/deadline controls, not an automatic process retry.

`notification_store` requires its own `control_schema`, `owner_role`, `publisher_role`, `reader_roles`, and `source_attempt`. Its schema may differ from the registry schema. `source_attempt` contains exactly the original `run_id`, `attempt_id`, and UTC `attempt_started_at`; this evidence confers no lease, approval or publication authority. The notification DSN must directly authenticate a configured Store reader. The execution DSN must directly authenticate `execution_role`, distinct from the reader and protected owners. Both actual login roles must permit LOGIN and have none of SUPERUSER, CREATEDB, CREATEROLE, REPLICATION or BYPASSRLS, directly or through membership in an elevated role. Server-file, execute-program, all-data, signal, checkpoint and subscription role memberships also refuse. Protected ordinary NOLOGIN owner SET access required by the existing native writer plan remains subject to that plan and custody guards. The connection wrapper performs no role switching, grants, role creation or schema bootstrap DDL; the existing verified consumer retains its protected candidate-publication operations.

The execution pool permits one connection. The independent SQLAlchemy notification engine permits one connection with no overflow, repeatable-read isolation and read-only transactions. Native SQL limits are checked on each raw and adapted checkout. Optional `sql_limits` contains all six integer fields: `work_mem_bytes`, `maintenance_work_mem_bytes`, `temp_file_limit_bytes`, `statement_timeout_ms`, `lock_timeout_ms`, and `connect_timeout_seconds`. Defaults are 16 MiB work memory, 64 MiB maintenance memory, 256 MiB temporary files, 120 seconds per statement, 5 seconds per lock, and 5 seconds to connect. The operator must provision a finite effective temporary-file limit; the worker refuses an unavailable or excessive limit rather than granting itself privilege. Parallel query and maintenance workers are disabled for these connections. Host CPU, disk, data and WAL quotas remain operator responsibilities.

Standard output contains only `{"state":"..."}`, where state is `completed`, `replayed`, `busy`, `review_required`, `stale_source`, or `conflict`. Event IDs, manifests, source evidence and credentials are never emitted. Configuration errors exit 2, worker errors exit 1, cancellation exits 130; diagnostics contain constant codes. A returned state exits 0, and the operator decides any later action. Work drains before owned connections close. The worker does not delete notifications, acknowledge an inbox, acquire approval, or launch a retry loop.

Accepted retained snapshots refresh asynchronously. Source freshness is checked by the connected consumer before work, and registry publication retains its approved/head comparison. This command does not promise strict latest-Source identity at registry cutover. Deployment grants, source producer/principal integration and operational acceptance require separate validation.


## Import control adapter

The registered importer `registry-cms-source-worker` uses queue `arq:RegistryCMSSource`, worker class `process.RegistryCMSSource`, and the existing `control_single_job_start` lifecycle. Its target is `process.registry_cms_source_worker.control_start`. The control API accepts exactly `source_schema`, `receipt_id`, and `notification_sha256`; none of the CLI connection, role, coordinate, attempt, path, SQL or environment settings can be supplied by a request. The queued source_schema must match the trusted operator environment scope; receipt_id and notification_sha256 may identify future committed notifications. The complete new coordinates come only from a verified Store.read, constrained to the configured coordinates' source_system/source_id/dataset_schema/producer_id and the configured Source endpoint. Caller coordinates are never accepted. The consumer still requires exact approved bindings for that actual new edition, using the latest custom revision. Explicit CLI invocation continues to use its exact configured receipt/hash and fixed coordinates.

The dedicated ARQ worker has one job, one queue read, one try and a finite 4200-second job timeout. The consumer's operation deadline remains at most 3600 seconds; the outer allowance leaves time for connection setup and native cancellation/drain. Existing control cancellation is observed while work runs, and the target drains consumer cleanup before the standard wrapper projects a terminal state. Success output contains only the consumer state. No inbox selection, coalescing, automatic replay loop or schedule registration is introduced.

Deploy this worker with its dedicated configured native execution principal and the existing launcher resource-profile mechanism. The operator must supply finite CPU and RAM requests/limits for `process.RegistryCMSSource` or its queue; this adapter does not create roles, grant privileges or provision host quotas. Local adapter tests do not establish launch, native publication or scheduling acceptance.


## Periodic refresh and replay

Control dispatch accepts only the Source-owned three-field notification identity. Receipt metadata discovers work; it grants no authority. A genuine read-only repeatable-read Store.read verifies the immutable notification, pair, receipt and Source custody before coordinates are selected. The stable source family and endpoint come from operator configuration, not labels or request data.

Under the existing source-family lock, the consumer searches published event checkpoints by the exact notification digest before deriving a fresh old slot. A checkpoint must preserve the full pair digest, canonical new recipe digest, original new/old coordinates, event digest, attempt and physical candidate identity. Lost-ack replay reuses that exact published candidate even after the current serving head changes. Malformed, conflicting or duplicate checkpoints refuse; they do not become fresh work.

Without a checkpoint, a pinned current manifest must retain exactly one source recipe in the configured family and endpoint. Its actual coordinates become the replacement slot. Zero or multiple matches return review_required. With an empty serving head, periodic control can build the initial manifest from the notification’s authenticated recipe and address snapshot, provided the actual new coordinates have exact current approved bindings. Missing bindings return review_required and leave the head empty. New exact approved bindings remain mandatory; prior network mappings and old edition labels are never carried forward. Source-current freshness and registry head/custom comparison retain their existing behavior. The initial event records mode=initial with null prior coordinates and a null base manifest. It uses the existing initial-source recipe, complete office validation and native head-zero/custom-revision comparison. Its published replay validates that exact initial candidate even after a later serving head, and never reactivates it. Explicit fixed-replacement CLI configuration remains unchanged. Inbox coalescing and schedule/event registration remain separate concerns.


Periodic control does not require per-edition operator configuration changes. The configured coordinate dataset/edition and replaced_coordinates remain the explicit CLI recipe; control uses only the configured stable family and endpoint, then verified notification/retained recipes provide each event's actual editions. Each read uses the complete original attempt decoded from that notification. The Store constructor's configured tag never replaces that evidence or authorizes a new attempt.


Completed, failed and canceled control run keys participate in all-status event idempotency. A reused key or active-run fallback must retain the exact three event parameters; a different event refuses rather than borrowing another run. Existing exact-attempt worker-absence reconciliation applies to this importer. The existing control wrapper persists the returned constant state in Run.metrics.state, including completed, replayed, stale_source and review_required. These fields describe this verified event outcome; caller parameters cannot supply a terminal state. Schedule retirement/recovery policy remains owned by the external control scheduler.


Each periodic attempt resolves its unique current OLD slot and computes the replacement event/attempt from the same snapshot as the serving manifest and latest approved map. An ordinary authorized publisher can therefore replace A with B while C is waiting without forcing a false missing-slot review. Bounded retry repeats checkpoint-first discovery after existing head/custom CAS refusals or exact PostgreSQL serialization error 40001. Serialization retries occur only after the transaction has rolled back; an open transaction, privilege errors and unrelated failures are not retried. Retry exhaustion returns conflict. Actual competing native cutover and serialization-barrier acceptance remain separate qualification work.
